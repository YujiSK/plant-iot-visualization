## 詳細時系列

### 2026-04-25から04-26: 最初の試作

- Raspberry PiとSense HATによるPlant IoT試作を開始した。
- 温度、湿度、気圧を取得し、SQLiteへ保存した。
- 単純な温湿度評価からvitalityを算出した。
- Supabaseへの送信を追加した。
- GitHub Pagesで最新状態を表示できるようにした。
- 発表用のデモモード、HTML検証、CIを追加した。
- Sense HATのLED表示を短時間で消灯する運用へ変更した。

この段階の目的は、センサー取得からクラウド保存、Web表示までの基本経路を成立させることだった。

### 2026-04-26: 枯死候補A

- 後の再分析で、02:57-09:10 JSTに高温・低湿度の連続記録を確認した。
- 復元後のSense HAT出力は平均36.46℃、平均湿度30.35%だった。
- 当時は植物写真、給水、しおれ始め、枯死確認時刻が十分に記録されていなかった。

Sense HAT温度にはRaspberry Pi基板発熱が含まれるため、実際の室温とは断定できない。

### 2026-05-12から05-14: 枯死候補Bと温度補正

- 5月12日にSense HAT温度へ固定オフセット`-8℃`を適用するコードを追加した。
- 補正は基板発熱を考慮する目的だったが、基準計との比較や校正試験は行っていなかった。
- 5月12日11:01から14日00:32 JSTに、最も長い高温・低湿度候補期間を確認した。
- 復元後のSense HAT出力は平均39.74℃、平均湿度30.54%だった。

この期間のDB行は補正導入前のものが中心で、保存値をSense HAT出力として扱える。

### 2026-05-13: 開発履歴管理の導入

- `PROJECT_LOG.md`と`NEXT_ACTIONS.md`を中心とする引き継ぎ運用を導入した。
- 会話履歴だけに依存せず、判断、変更、未完了事項をリポジトリへ残す方針にした。

### 2026-05-18: 枯死候補C、湿度補正、管理アプリ試作

- 温度補正`-8℃`に加え、湿度へ`+15ポイント`の固定補正を導入した。
- 同日09:38頃から温度補正を`-15℃`へ変更した。
- 補正量は校正試験ではなく、値を想定範囲へ近づける目的で設定された。
- 補正後の値だけがSQLiteとSupabaseへ保存された。
- 02:35-09:58 JSTを枯死候補Cとして抽出した。
- 復元後のSense HAT出力は平均41.07℃、平均湿度25.71%だった。
- 09:10 JSTに`care_logs`の確認記録が残っている。
- Flutter管理画面と`care_logs`の最小実装を追加した。

後の再調査で、この補正処理は研究データの扱いとして不適切だったと整理した。

### 2026-05-19から05-25: Sense HAT運用継続

- 温度`-15℃`、湿度`+15ポイント`の固定補正を継続した。
- 5月23日のCodexセッションログに、補正前後の完全な値4件が残った。
- このログが後の復元根拠になった。

### 2026-06-02から06-05: 現配線への移行と枯死候補D

- Sense HATをやめ、DHT11とMCP3204/MCP3208 ADCを使う構成へ移行した。
- DHT11の値は固定補正せず、そのまま保存する方針にした。
- ADC CH0で水位、CH1で照度を取得した。
- Supabaseへ水位・照度カラムを追加した。
- 候補D期間のDHT11生値は平均25.71℃、平均湿度61.04%で、高温・低湿度は確認されなかった。
- 水位ADCは全記録0だった。

この4回目の失敗は、高温よりも次の給水経路の問題が有力と整理した。

- 養液不足
- フェルトの吸水不足
- 根とフェルトの接触不良
- 水位センサー位置または配線状態

正確な植え替え、養液変更、枯死確認時刻は未記録のため、原因は確定していない。

### 2026-06-08: 表示と手動運用の改善

- GitHub PagesとFlutter表示をDHT11・水位・照度構成へ更新した。
- systemdサービスを再起動せずに手動送信できる機能を追加した。
- 5分境界に送信時刻を合わせた。
- GitHub Pagesへ水位、温度、照度に応じた助言表示を追加した。
- Plant Doctorパネルを追加し、後に表示を簡略化した。

### 2026-06-11: 配線情報のコード管理

- Raspberry Piとセンサーの配線を`WIRING.md`へ整理した。
- Graphvizから配線図SVGを生成する仕組みを追加した。
- 実装コードだけでなく、実機構成もGitで追跡できるようにした。

### 2026-06-12: 養液温度と過去分析

- DS18B20を追加し、養液温度を記録できるようにした。
- センサー再接続後、DHT11、DS18B20、ADC、ローカルAPI、Supabaseの統合動作を確認した。
- 過去ログから枯死候補A-Dを整理した。
- 水位センサーだけでは、貯水部の水と、フェルト・根まで水が届いたかを区別できないと整理した。
- BH1750への照度センサー移行を準備した。

### 2026-06-13: 2台構成と実栽培開始

- 1号機`raspi`と2号機`raspberrypi2`へ役割を分離した。

1号機:

- DHT11
- DS18B20
- ADC水位
- ADC照度
- 動作確認用ノード

2号機:

- BH1750
- DS18B20
- GPIO17フロートスイッチ
- 実際のバジル栽培環境

- Supabaseへ`device_id`と`location_id`を追加した。
- 一部センサーが失敗しても、取得できた値を送信し続ける構成にした。
- BH1750の配線を修正し、常駐サービスから照度を送信できるようにした。
- vitalityを養液温度、照度、水位、温湿度の複合評価へ拡張した。
- BH1750は青色蓋の容器内に設置されているため、葉面照度ではなく相対指標として扱う方針にした。

### 2026-06-13 06:30以降: 設置初日の安定区間

- 2号機を実栽培環境へ設置した。
- 06:30-19:50 JSTはフロート163件すべてが`water_ok`だった。
- 養液温度は24.875-28.062℃だった。
- BH1750は日周変化を記録した。
- 日次センサー分析を作成した。

この日の分析は栽培成果ではなく、設置初日の計測系検証として位置づけた。

### 2026-06-13 21:44: 発芽・子葉展開確認

- 写真で複数個体の発芽と子葉展開を確認した。
- 本葉は未確認だった。
- ろ過ウール表面は湿潤状態に見えた。
- 明確なしおれ、黄化、枯死は確認されなかった。
- 観察内容をSupabaseの`care_logs`へ保存した。

### 2026-06-13 21:45以降: 写真とセンサーの差

- 最寄りのセンサーログはフロート`low_water`だった。
- 写真は培地表面、フロートは貯水部を観測しており、対象が異なると整理した。
- 人間観察だけでも、センサーだけでも、植物管理に必要な全情報は得られないと分かった。

この事例が、研究方針を管理支援へ転換する主要な根拠になった。

### 2026-06-14: 旧補正データの復元

- 1号機の原本`data.db`を読み取り専用で調査した。
- Git履歴、`.env`、DBの値の段差、Codexセッションログから補正期間を確定・推定した。
- 元DBを変更せず、固定オフセットだけを逆算した。
- 7,330行をCSVへ復元した。
- 復元期間不明の行は0件だった。
- 原本DBのハッシュ、補正期間、復元根拠をメタデータJSONへ保存した。
- 補正を適用した事実、不適切だった判断、是正過程を削除せず記録した。

復元値は校正済みの室温ではなく、補正前のSense HAT出力である。

### 2026-06-14: 研究方針の転換

研究主軸を次のように変更した。

```text
変更前:
植物を自動で育てる
植物を枯らさない
自動給水する

変更後:
植物の異常発見・観察・記録を
継続しやすくする管理支援システム
```

研究対象を植物そのものの自動制御ではなく、次の管理行動の支援とした。

- 異常発見
- 観察
- 記録
- 対応
- 回復確認
- 振り返り

研究仮説:

- H1: IoT通知が異常対応時間を短縮する
- H2: AI観察支援が観察記録の欠損を減らす
- H3: 日次分析と`care_logs`が振り返りを容易にする

### 2026-06-14: Slack中心の実験方針

- LINE、Slack、Flutterを比較した。
- 研究期間中はSlackを実験基盤として採用した。
- Flutterは有効性を確認した機能の最終移植先とした。

段階:

1. Slack異常通知
2. 回復検知と`care_logs`生成
3. 写真観察支援
4. 再撮影支援
5. 観察品質評価
6. Flutter移植
