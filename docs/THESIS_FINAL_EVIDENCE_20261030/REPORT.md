## 3. 学術的整理

### 3.1 Research Problem
植物管理を支援するIoTシステムは、多くの場合「データが取れている」ことで評価される。しかし実環境では、記録が存在しても必要な測定値が有効とは限らない。また、毛細管（フェルト）給水が植物側まで成立しているかは、水位センサーだけでは観測できない（9/18の方向性文書）。

### 3.2 Proposed System
- 2台のRaspberry Pi：1号機（DHT11・DS18B20・MCP3208、屋内の動作確認用）、2号機（DS18B20・BH1750・フロート、屋外）
- 5分周期でSupabaseへ送信。7/22以降はSQLite Outboxによる再送を導入
- GitHub PagesでのWeb可視化、LINE・Slackの低水位・送信障害通知、Slack写真→AI観察記録
- 10/13以降：MCP3204による水分プローブADCを60秒周期でローカル記録

### 3.3 Experimental Setup
屋外の実栽培装置（バジル。8/2の転倒事故後は栽培が継続していない）。評価期間は6/13〜10/13（クラウド）と、10/13〜10/30 17:53（水分ADC）。介入の記録は、`care_logs`（〜9/9）と、SQLiteのイベント1件だけである。

### 3.4 Evaluation Metrics
- 5分枠の記録存在率（A）
- 3センサー有効率（B）とセンサー別の有効率
- 最長空白
- 測定→クラウド同期の遅延（C：中央値・p95・p99）
- 再送件数と重複件数
- ADC連続性（期待件数・欠測・最大間隔）、ADC記述統計、飽和率（≥4094）、変化点候補

定義の詳細は QUANTITATIVE_RESULTS.md §0 と MOISTURE_EXPERIMENT.md §2・§5 に記した。

### 3.6 Discussion
- **AとBの乖離**：9/9以降、送信プロセスとGPIOのフロートは動き続けた。一方で、1-WireとI²Cの2センサーが同時に失われた。センサー読み取りの例外をNoneとして吸収する設計は、送信を止めないという意味で可用性を優先している。その代わり、欠測が「正常な記録」に紛れ込んだ。さらにvitalityが欠損を加点も減点もしなかったため、指標は最高値になった。**記録の継続性を信頼性の代わりに使ってはならない**ことを、実データで示す事例である。
- **Outbox**：9月以降は、ほぼすべての測定が1秒前後で到達し、一時的な失敗も次の周期で回復した。ただし冪等キーがないため、at-least-once（少なくとも1回）配送による重複が実際に1件発生した。
- **水分実験**：60秒周期の安価な計測系は欠測なく動いた。しかし、①条件変更が記録されていない、②レンジが飽和した、③校正していない、という3つの欠落のため、給水構造の評価には使えない。1分以内の段差（10/16 11:40、10/18 21:02）は離散的な事象と整合するので、条件の時刻を復元できれば、事後的に対応付けられる可能性がある。
- **事故事例**：8/2の多項目急変と39時間の途絶は、「検出できたもの」（記録の途絶・値の急変）と「検出できないもの」（転倒そのもの、植物の水分状態）の境界を示す。

### 3.7 Limitations
- 単一装置・単一栽培期の事例研究であり、反復がない。
- 栽培条件・設置条件が期間の途中で変わった（事故、栽培終了、センサーの欠落）。
- 9/13より前のクラウド到達遅延は測定できない。
- 通知の到達・利用者の応答の記録がない。
- AIの精度は評価していない。
- 水分ADCは未校正で、条件の記録がなく、10/19以降は飽和している。
- 7月の障害原因と9/9の欠損原因は作業記録（B）または推論（C）にとどまる。

### 3.8 Research Contribution（過大評価しない範囲）
1. 植物管理IoTの屋外運用で、**記録存在・有効測定・到達遅延を分けて定量化**し、その乖離を実データで示した（86.61%対59.02%、99.86%対0.01%）。
2. 失敗モードの具体例を挙げ、設計上の要件を導いた。「欠損時に健康指標が最高値になる」「再送で重複が生じる」「異なるバスのセンサーが同時に失われる」といった例から、センサー存在の監視、冪等な送信、イベント注記の必須化が必要だと分かった。
3. 低コストの水分ADC計測系で長期連続記録が可能であることと、その計測レンジの限界（開放時の水準で飽和）を示した。
